# Abaqus AMS 运行期观测清单

> 本文档整理 Abaqus/Standard 运行 `*FREQUENCY, EIGENSOLVER=AMS` 时，从各输出渠道
> 能观测到的**内部行为证据**，作为"黑盒逆向 AMS 技术细节"的采集清单。
> 目标：在 Abaqus 重装完成后，跑一次 AMS job，把下面每项都采到，用于
> 对照我们 AMLS 实现（见 `docs/AMLS_实施计划.md`）逐项定位差距。
>
> 状态：**待 Abaqus 重装完成后实测采集**。本文内容是"该去观测什么"，
> 不依赖 Abaqus 能否运行。

## 1. 求解器阶段划分：从 .msg 文件观测

Abaqus/Standard 求解器的 `.msg` 文件（`jobname.msg`）记录每个增量步/求解阶段，
是观测 AMS 内部阶段的最直接渠道。AMS 频率提取作为一个 STEP 内的分析，其阶段
推进会以类似下面的形式出现在 `.msg`：

```
STEP 1 (freq)
 *Analyzing frequency extraction with AMS eigensolver
   ...  (各阶段)
 STEP COMPLETED
```

**要观测的字段**：
- 阶段名称：AMS 是否有明显的阶段分割（如剖分 / 变换 / 求解 / 恢复）。
- 每阶段是否报告耗时、内存。
- 迭代次数、收敛信息。

> 注：Abaqus 对 Eigenvalue/AMS 的输出比显式动力学的增量步输出少，但 `.msg`
> 一定有 STEP 边界和分析类型标记。装好后第一件事就是把 `.msg` 全文存档。

## 2. 内存：.dat 文件的内存估算

Abaqus 在 `.dat` 文件开头（分析前）打印 **memory estimate**：

```
 MEMORY ESTIMATE
 ...
 MINIMUM MEMORY REQUIRED = xxx MB
 MEMORY REQUIRED FOR ANALYSIS = yyy MB
```

**要观测的字段**：
- MINIMUM vs REQUIRED：AMS 的峰值内存估算（这是 Abaqus 自己算的，比任务管理器准）。
- 这个数字与模型规模 n 的关系（扫一个规模阶梯，看它是线性/超线性增长）。
- 对照我们 `amls_solve` 的 `# 内存: 峰值工作集`。

## 3. 性能摘要：.dat 尾部的 timing 汇总

Abaqus 在 `.dat` 文件尾部通常打印各阶段墙钟：

```
 TOTAL WALLCLOCK TIME = ...
 TOTAL CPU TIME = ...
```

**要观测的字段**：
- 总墙钟 / 总 CPU。
- 是否分阶段（有些版本有 per-analysis time breakdown）。

## 4. 环境变量：控制 AMS 行为的隐藏开关

Abaqus 支持大量 `ABA_*` 环境变量（前面 `information=all` 已确认存在
`ABA_...` 列表）。AMS 相关的、以及能影响内存/求解的，值得逐一尝试：

| 变量 | 作用（推断，需实测） | 观测目标 |
|---|---|---|
| `ABA_STD_ACTIVATE_CONTACT_FOR_AM` | 接触参与 AMS？ | 我们无接触，无关 |
| `ABA_RESOURCE_MONITOR` / `ABA_RESOURCE_USEMALLINFO` | 内存资源监控开关 | 开启看是否能拿到更细内存曲线 |
| `DOUBLE_PRECISION` | 全局双精度 | 对比单/双精度对耗时/内存影响 |
| `ABA_MEMORY_MODE` | 内存模式 | 省内存策略的开关 |
| `NCPUS` / `OMP_NUM_THREADS` | 核数 | 并行扩展性观测 |

> 这些变量的**确切效果必须实测**（黑盒）。标记 [INF]（推断），不当作定论。

## 4b. 已实证的环境配置（来自本机 `abaqus_v6.env`）

重装前从 job 生成的 `.env` 文件（`bench_abaqus/cant_3x3x3.env`）里已确认
以下配置，它们直接影响 AMS job 的行为：

- **`freqEigenAMS: {'ams': ON}`**（`aba_jle_exclusions` 条目）：Abaqus 把
  `*FREQUENCY, EIGENSOLVER=AMS` 作为 **JLE（Job Launch Engine）专用任务类型**
  处理——AMS job 走了独立的启动/调度路径，与普通增量分析不同。
  重装后可据此判断：AMS job 的 `.msg`/`.log` 会与普通 job 有结构差异。
- **`aba_jle_std_direct = 10,20`**、**`aba_jle_std_direct_memlimit = 8gb`**、
  **`aba_jle_std_direct_reqcpus = 32`**：Standard 求解器在"直接求解器 vs 迭代
  求解器"间的 JLE 切换阈值（内存 8GB、32 核）。大模型 AMS 的内存估算可能与
  这些阈值相关（直接法被 JLE 限制时 AMS 可能走迭代路径）。
- **`aba_jle_std_mbld = 6,12,24,48`**、**`aba_jle_std_iterative = 4`**：MBLD/
  迭代求解器的并行配置。
- **`aba_jle_xpl_all = 1`**：Explicit 全功能许可。

重装后：跑 AMS job 前先 `information=all` 再存一次 `.env`，确认这些配置是否
变化（不同安装包可能不同）。

## 6. 进程级观测（Windows）

- 任务管理器 / `GetProcessMemoryInfo`：AMS 进程的峰值工作集。
- 时间：`Measure-Command` 或手动记录墙钟。
- CPU 时间：任务管理器进程页 / `GetProcessTimes`。

**与 AMLS 侧对齐的口径**：
- 我们 `amls_solve` 输出：`stage=... wall_seconds cpu_seconds` + 峰值工作集。
- Abaqus 侧：`.dat` 的 memory estimate（内存口径是 Abaqus 估算） + 墙钟 +
  进程峰值工作集。两者内存口径不同，报告时**分别标注**。

## 7. 矩阵导出：*MATRIX GENERATE 的输出格式

`*MATRIX GENERATE, STIFFNESS/MASS, GLOBAL, FORMAT=COORDS` 导出 K/M 到
`jobname_STIF.mtx` / `jobname_MASS.mtx`（Harwell-Boeing 坐标格式）。
**要确认**（装好后小模型试跑）：
- 实际文件名（`_STIF.mtx`? 还是带 step 编号）。
- 格式细节：是否对称、是否含对角线、行列号 1-based。
- 能否直接给我们的 `readMatrixMarket`（它支持 coordinate + symmetric）。

## 8. 采集协议（跑 AMS 时固定记录）

对每个模型规模，固定记录一份 `meta.json`：

```json
{
  "model": "cant_100x50x20",
  "n_dof": 1000000,
  "nev": 200,
  "nproc": 8,
  "wallclock_s": 123.4,
  "cpu_s": 450.0,
  "dat_memory_estimate_mb": 2048,
  "process_peak_working_set_gb": 3.2,
  "freq_first_10_hz": [ ... ],
  "msg_stages": "...",
  "matrix_export_files": { "K": "job_STIF.mtx", "M": "job_MASS.mtx" }
}
```

> 采集后：K/M 喂 `amls_solve --K --M` 求同一问题，特征频率对比 + 耗时/内存对比。

> `tools/run_abaqus_ams_bench.py`（待写）。
